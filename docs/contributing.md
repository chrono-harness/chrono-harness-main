# Issue、分支与 PR

这些约定适用于 chrono-harness 组织的独立仓库。首次贡献先读负责仓的 `AGENTS.md`，按其中的命令检查改动。跨仓目标在入口仓跟踪，各产品分别在自己的仓库开 Issue、提 PR 和验收。

## Issue 怎样命名、分类

标题用一句话描述可观察的问题或想要的结果，例如「PR 进入冲突后立即返回」或「发布重试后仍有两条故障单」。创建前搜索同仓的开放及已关闭事项。需要多个 PR、下游采用或后续跟踪时开 Issue。一次 PR 即可验收的小改动可以直接提交。

普通 Issue 选下表中的一个主标签。网页表单按所选类别带入标签。通过 CLI 创建时用 `gh issue create --label <主标签>`，通过 API 创建时设置 `labels`。分类变更时只更换主标签，保留其他有效标签。

| 主标签 | 什么时候选 | 正文写什么 |
| --- | --- | --- |
| `bug` | 已有行为偏离预期 | 版本或 SHA、复现步骤、预期与实际结果，附原始失败 |
| `enhancement` | 新能力、行为改进、工程任务或跨仓路线图 | 谁需要、要交付什么、依赖什么、怎样验收 |
| `documentation` | 交付物是指南、示例说明或参考文档 | 哪位读者在哪一步遇到困难，读完应能完成什么 |
| `question` | 需要解释用法或确认行为 | 目标、所用版本、已试方法、具体问题 |

发布自动化按运行 ID 创建并维护带 `release-failure` 的故障单。同次运行重试成功由工作流关闭，后续版本修复时引用原故障单和成功运行。第一个字段保留原运行标记，以便自动化识别。

额外标签按用途叠加。`accessibility` 标出无障碍影响，`help wanted` 表示可领取，`good first issue` 用于范围清楚且有入门指引的任务。标 `duplicate` 时链接原事项，标 `invalid` 或 `wontfix` 时说明判定或取舍。开放、关闭和关闭原因用 GitHub 原生状态，排期用 Milestone。路线图需要区分先后时在正文说明 P0（当前故障或交付阻塞）、P1（缺少的能力）或 P2（依赖上游交付的验收），附上阻塞关系。

## 分支怎样命名

从最新 `dev` 建短期分支。`feature/` 用于单项功能、修复或文档，`integration/` 用于规则、门控、稳定性或关联变更的集成验证。后面写小写英文短语，用单个连字符分词，可以在词中使用数字。有本仓 Issue 时，将正整数编号放在短语前。同仓并行处理一个 Issue 时用不同的短语描述各自交付。

| 场景 | 示例 |
| --- | --- |
| 为本仓 Issue #42 修复冲突返回 | `feature/42-report-pr-conflicts` |
| 为同一 Issue 验证合并流程 | `integration/42-check-merge-flow` |
| 一次可验收的独立文档改动 | `feature/document-release-tags` |

普通工作分支可以用以下正则整串匹配。例中编号指当前仓库的 Issue，跨仓编号在 PR 正文使用完整引用。发布流程和宿主登记的长期分支另按其用途命名，如 `dev`、`main` 及示例的配置分支。

```regex
^(feature|integration)/([1-9][0-9]*-)?[a-z][a-z0-9]*(-[a-z0-9]+)*$
```

## PR 怎样写、怎样合入

1. **标题**用 `type(scope): 结果`，scope 可省略。type 从 `feat`、`fix`、`docs`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert` 中选择。破坏接口可在冒号前加 `!`，并在正文写明受影响的使用方及迁移方法。例子是 `fix(pr): 冲突时立即结束等待` 或 `docs: 补充正式版安装步骤`。
2. **正文**说明改动和使用方、关联 Issue、实际执行的检查和结果，以及剩余验收。可以复用 CI 链接。按仓库选择的身份规则，由执行操作的 agent 附上真实配对事件。
3. **关联与关闭**分别处理。跟踪局部进展用 `Refs #42`，跨仓用 `Refs owner/repo#42`。只有合入默认分支即可满足该 Issue 的全部验收时，才用 `Closes #42` 或 `Closes owner/repo#42`。尚待发布、落地 CI 或真实下游采用时继续跟踪，取得对应证据后关闭。先合入 integration 的阶段 PR 使用 `Refs`。
4. **合入**以负责仓登记的目标和检查为准。日常 PR 目标为 `dev`，需分阶段集成时先进入该 integration，验收后由 integration 向 `dev` 提 PR。`main` 用于晋升已验收的正式版。独立 PR 可并行验收。head 更新后用新 SHA 核对，冲突时解决冲突并验证受影响范围。
5. **交付**时记录合并 SHA、实际落地检查和 Issue 要求的发布或下游证据。使用该仓已启用的合并方式与必需检查。等待 PR、push 或 CI 时使用完成事件；终态后核对原运行。验证完成后清理已交付的短期分支和工作树。

分支名和 PR 标题从新工作开始采用。网页表单、根指南和 CLI 约定向贡献者提供相同的分类与提交流程。各仓的合并保护和发布验收以自身登记为准。
