# 在 Chrono Harness 里怎样做决定

一份报告写完，谁会打开它？假如明天删掉生成它的代码，谁会失去什么？这两个问题要先于实现。一个真实的回答可能是「用户下一次打开 PR 时，需要看到哪条测试失败」。这就给了我们一个能验收的结果。仅仅知道「CI 会上传文件」，还要再问一句，谁会下载？

## 第一次进仓库，能独自工作吗？

每个仓库，包括工具仓，都从模板接入。人从 README 开始，agent 从根目录的 AGENTS.md 或 CLAUDE.md 开始。二者应能找到本仓做什么、怎样安装、改动后跑哪条检查。通用指令在上游维护，默认全部接纳。宿主可以按条关闭、只选几条，也可以追加自己的约定。上游通过模板的规则同步入口交付。[模板和选装](../README.md#在自己的项目中使用) · [公共指令](https://github.com/chrono-harness/chrono-harness-instructions)

工具各自建仓、构建、验证、发布。本仓是地图。打开地图应当能找到修工具的地方，安装一个工具应当只需要它公开的发行件和接口。跨仓源码路径、依赖相邻检出的构建脚本，会让搬走一个仓库就足以弄坏另一个。共享工具、依赖和证明配方各在负责处定义一次。模板默认选中工具，项目可以取消用不到的项。[组件与接口](../README.md#仓库如何配合)

## 谁接住一次失败？

程序离故障最近。它知道哪次读写失败、处理了多少、哪一步已经生效。它应把这些事实、原始异常及其原因链交给调用者，清理自己持有的资源。AI 有更广的上下文，可以看另一个任务是否仍在写、磁盘上什么可以回收、失败是否总落在同一行。把判断交给知道答案的一方。

读固定输入时断了网，AI 可以在原期限内退避后再读，核对版本和摘要。一批编译进程把内存用尽，先等竞争者退出，或在登记的资源约束内减少同批并发。磁盘满时，先按业务目录回收已到期且无人使用的产物，确认腾出了空间，再接着写。程序因输入不合法而报错，修输入或解析器。一个错误号，常常对应几种不同的下一步。

把有副作用的操作想成一次转账。没拿到回执，钱可能已经到账。先用原操作身份查账。查实已经生效，就接着验收。查实旧操作已经终结且没有生效，或服务对同一标识保证去重，才有安全重放的依据。AI 自主做授权内的处置，保留第一次失败。相同原因反复出现，就在产生处修复并留下能重现它的用例。原结果查不清时写「未知」，继续独立的工作。

这个差别在工作树里发生过。目录已经建好，通知用的管道却断了。旧程序退出 101，调用方连新目录的报告都没收到。修复后，调用方能读到已建目录和原始报告。另一次调度验收让两个任务同时争用输出目录，再换成两个独立目录，直接观察哪个任务应该等。[管道断开的实际结果](https://github.com/chrono-harness/chrono-harness-worktree/issues/93#issuecomment-7212452241) · [九组并发调度](https://github.com/chrono-harness/chrono-harness-judge-projects/issues/79#issuecomment-7201831317)

## 一项工作结束，桌上该留下什么？

Git 保存源码和项目约定。中断后可以从一次干净检出重来。任务的中间文件放在对应工作树，工作树结束时按业务目录回收。共用的安装包交给安装器的缓存。日志有滚动窗口，PR 的本地提醒也要过期。GitHub 缓存已有平台清理，直接用它。每多保留一份输出，写清谁要读、最晚何时读、谁来删。

有价值的成果在窗口内送到选定的持久存储，核实对方已收到。清理前核对实际路径、活跃使用方和未保全的独有工作。借用工具还握在别人手中，到点应提醒归还；钟响本身不能把工具从别人手里拿走。[业务目录的回收](https://github.com/chrono-harness/chrono-harness-main/issues/30)

## 进度怎样让人看明白？

需求在负责仓开 Issue，写出使用方与通过条件。PR、检查和交付保留 agent、会话、模型和固定提交。并行的几个 agent 可以各有署名。等待用事件；PR 冲突、换了 head，或 CI 结束，收到相应变化再行动。下次会话从 GitHub 重查，本地提醒只帮忙记住要查哪个 PR。[协作约定](contributing.md)

开发先进 dev。正式版从已验证的候选晋升 main。用户可在任何分支选正式版、测试版或确切版本，每次安装按所选通道解析。项目依赖与 Actions 交给 Dependabot，必需检查通过后自动合入 dev。路线图上把「已合入」「已发布」「使用方已经用过」写清楚，读者才能判断自己现在可以做什么。[版本与更新](../README.md#在自己的项目中使用) · [实时路线图](https://github.com/chrono-harness/chrono-harness-main/issues/15)

## 怎样知道一条规矩值得信？

挑一个它最容易答错的情形。比如写入已经成功，只有回信丢了。把动作、可观察的证据、允许的下一步写成模型，让机器寻找能导致第二次写入的路径。再故意放开那条限制，看它能否给出反例。实际工具还要用固定源码、原生错误和真实下游核验模型的前提。文件到期后最终可以删除，就要说清最后一个使用方何时离开、维护程序何时得到执行机会。[写入重放的可执行模型](https://github.com/chrono-harness/chrono-harness-instructions/blob/fabc9c51c9e1fa5bec811998e04db6cfc4f3a655/docs/recovery-model.md) · [工作树回收证明与验收](https://github.com/chrono-harness/chrono-harness-worktree/issues/23) · [生产判断与证明的对应关系](https://github.com/chrono-harness/chrono-harness-judge-projects/issues/23)

写给读者时，也用得上这个办法。把「异常恢复机制已生效」改成「磁盘满了，程序留下写到一半的文件名；腾出空间后，AI 核对长度，再从安全位置接着写」。读者能指出哪一步可能错，这段话才给了他判断的余地。
